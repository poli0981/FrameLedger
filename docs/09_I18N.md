# 09 — Internationalization

Languages: **en** (neutral/default) · **vi** · **ja**. Same `.resx` pattern as the rest of the poli0981 portfolio.

## Mechanics

- One `Strings.resx` (+ `Strings.vi.resx`, `Strings.ja.resx`) per assembly that has user-visible text (`App`, `Shared` for error codes). Access through a generated strongly-typed class; **no string literals in XAML/C# for user-visible text** (analyzer TODO: Meziantou MA0011/manual review in PR checklist).
- XAML binding via `{x:Static res:Strings.Key}` plus a `LocalizeExtension` for the few dynamic cases.
- **Runtime switching:** setting change → set `CultureInfo.CurrentUICulture` + `Thread` defaults → re-create the main window shell (cheap; state preserved via VM). Persist in `settings`.
- `SatelliteResourceLanguages` = `en;vi;ja` in the App csproj to keep publish size down.

## Key conventions

`Area_Element_Qualifier` — e.g. `Games_Header_Sessions`, `Update_Err_RateLimited`, `Chip_RT_Tooltip`. Error dialogs use the code as suffix (`Update_Err404`). Sort keys alphabetically; never reuse a key for different meanings.

## Formatting rules

- Numbers/dates through `CurrentCulture` (`{0:N1}`, `ToString("g")`); **charts and CSV exports always use InvariantCulture** (files must be machine-stable regardless of UI language).
- FPS readout format strings are resources too (`Fps_Fg_Format` = `"{0} → {1} FPS (×{2:0.0} FG)"`) so ja/vi can re-order if needed.
- No sentence concatenation; use composite format strings with placeholders.
- Pluralization: keep separate keys (`Sessions_Count_One`, `Sessions_Count_Many`) — en/vi/ja all survive this simple scheme.

## Translation workflow

- `en` written first, is authoritative.
- `vi` authored by the maintainer.
- `ja` machine-drafted, each entry marked with `<comment>review</comment>` until reviewed; the About dialog credits reviewers.
- CI check (`tools/resx-audit`): every key present in all three files; missing → build warning list artifact.

## Safety-critical strings

Consent, refusal, and safety-unhook text (FR-2.1, `19_SAFETY`) is **reviewed like legal text, not like UI text**:

- No machine-drafted `ja` in this category — a mistranslated ban warning is a real harm. These keys are marked `<comment>safety: human review required</comment>` and the `ja` build fails the resx audit until a human reviewer signs off; until then the `en` string is shown as fallback rather than an unreviewed translation.
- Never soften the wording per locale. "May result in a permanent ban of your account" must survive translation with the same force in all three languages.
- Key prefix `Safety_*` so they are easy to audit as a group.
